Triangulate

An agent that finds what a code change puts at risk by triangulating three views of the same product: what was intended (docs), what was built (the live UI) and how it was built (the code), joined in one Neo4j knowledge graph.

1TL;DR: the eight decisions

If you read only this section, you know the whole plan. Each decision is justified further down.

Target

Hoppscotch

Live app hoppscotch.io, code hoppscotch/hoppscotch, docs hoppscotch/docs. Code is pinned to tag 2026.9.0, the exact build that is live today (verified).

Crawler

Playwright + our own explorer

A systematic, replayable explorer, not browser-use. The LLM never clicks during the main crawl. A small, bounded probe agent hunts only for documented features the crawl did not find.

The bridge

UI text → i18n key → component

Every visible label in Hoppscotch comes from a translation key that a Vue component calls with t('…'). That gives a factual link from DOM to code. It is the main reason this app was chosen.

Graph

3 layers + 2 bridge nodes

Requirements, UI and Code layers. I18nKey and Route belong to both UI and code, so they join the layers by fact rather than by guess.

Absence

Explicit Gap nodes

Absence is a dated claim tied to one crawl run: “we looked here, here and here and did not find it”. A missing edge is never read as absence. The UI-vs-code “presence signature” decides the gap kind.

Confidence

Measured, not self-reported

Confidence comes from the method that produced a link, calibrated on small hand-labelled gold sets. We never use an LLM's “I'm 90% sure”. Uncertain items go to a human queue.

LLM

Claude Opus 5.5, one model

Effort is tuned per stage. Every LLM output must cite evidence that code then verifies (quotes exist, IDs exist). The Batch API handles bulk steps and a response cache makes runs replayable.

Depth

Deep on UI↔Code + PR reasoning

Requirements are scoped to the 26 feature pages of the docs. Only the logged-out web UI is crawled. Both cuts are stated openly in the design doc.

4Target app choice: Hoppscotch

Choosing the app is the highest-leverage decision. The brief says “anything with enough depth”. What actually matters is whether the three layers can be joined by evidence.

The five things a target must have

  1. Crawlable without a login. No credential handling, and anyone can reproduce the run.
  2. The public repo is the deployed code, at a version we can identify. Otherwise the code layer describes a different app.
  3. Product docs written as user features, not developer API docs.
  4. A deterministic DOM↔code bridge (test IDs, i18n keys, routes). Without one, every link is a guess.
  5. A steady flow of mid-size UI pull requests, for the demo and for evaluation.

Every stage writes its output to runs/<run_id>/<stage>/ before loading Neo4j. That makes each stage replayable and diffable, which the eval depends on.

Why this is an agent, not a chain of prompts

It has a goal and acts on the world

The goal is to find UI evidence for every documented feature. It chooses actions in a live browser, observes the results, and changes course: the frontier is re-ranked toward requirements that are still uncovered.

It knows what it doesn't know

Uncovered requirements trigger targeted exploration. What remains becomes an explicit, evidenced Gap. Low-confidence links go to a human queue instead of into the report as facts.

It has memory that compounds

The graph and the saved human decisions (overrides.yaml) carry over between runs. A human answers a question once, and the system reuses the answer.

LLM calls are bounded proposals

Five narrow LLM jobs, each with a schema and a code-side check. Everything that can be computed (versions, parsing, render trees, graph traversal) is computed, not prompted.

For each stage: what goes in, what comes out, who decides, why it's built this way, and what happens when it fails. Under the no-fallback rule, a failure is always explicit.

Stage 0 · Pin versions Deterministic

In
Live app URL, code repo, docs repo
Out
manifest.json: app version, code tag + commit SHA, docs commit SHA, crawl run id, config hash
Fails when
The version string can't be read from the live bundle, or no git tag matches it. The run stops: it is never “close enough”.

Read the version from the live JS bundle ("2026.9.0"), check out that exact tag, and record the docs commit. Every later artifact carries these IDs.

Why: the code layer is only meaningful if it describes the build we crawled. Most “DOM can't be mapped to code” failures are really version mismatches; pinning removes that whole class.

Stage 1 · Ingest docs → requirements Parse Extract Verify

In
26 MDX feature pages from hoppscotch/docs/documentation/features/ at the pinned commit
Out
requirements.jsonl: about 120–200 atomic requirements, each with a verbatim source quote
Fails when
The LLM output fails the schema after SDK retries (stage error). A requirement whose quote isn't found in the source is rejected and logged, never repaired.
  1. Parse det: markdown-it-py splits each page into a section tree (page → headings) with character offsets. MDX components and images are stripped to plain text.
  2. Extract LLM: for each section, Claude returns atomic requirements as a Pydantic schema: statement (“User can add request headers”), verbatim quote, feature, testability (UI_OBSERVABLE · NEEDS_LOGIN · OTHER_CLIENT such as desktop or CLI · NOT_UI), and UI cues (the nouns and verbs a user would see). Runs through the Batch API.
  3. Verify det: the quote must be an exact substring of its section (whitespace-normalised). IDs are stable: REQ-<feature>-<sha1(quote)[:6]>.
Why: turning prose into testable statements is what an LLM is good at; proving it didn't invent them is what code is good at. Stable IDs let us compare runs.

Budget: 250 states, depth 6, 30 minutes per run. “Seen?” compares the new state's fingerprint with every saved state.

The four design choices that make it work

  • State fingerprint. A hash of the route plus the sorted list of (role, accessible name) for structural elements: landmarks, dialogs, tabs, buttons, menus, fields. Numbers, URLs and editor or response contents are masked. Two screens that differ only in data are therefore one state, and the crawl doesn't explode.
  • Navigate by replay, never by Back. Every state stores its shortest action path from a seed route. To try a new action we open a fresh browser context and replay the path. Hoppscotch keeps tabs and history in localStorage, so a clean context per episode is what makes runs reproducible.
  • Inputs come from fixtures, not the LLM. The request URL is https://echo.hoppscotch.io (the app's own default), plus fixed header and parameter values. Same inputs every run.
  • Guardrails in code. Same-origin only; a denylist for sign-in, logout, delete, external links, downloads and install prompts; the third-party chat widget is blocked; roughly one action per second.

Screen labels LLM

After the crawl, Claude (vision, low effort, batched) gives each state a human name and a one-line purpose, e.g. “Request builder, Headers tab”. Labels are for readability only and are never used as linking evidence.

Why not browser-use or Stagehand? They are built to complete a task. We need to enumerate a state space with coverage guarantees, reproducibility and structured artifacts. Driving every click with an LLM would be slow, costly and different every run, and it would hide the artifacts the graph needs. We still use an LLM agent, but only where judgement adds value: the probe in Stage 5.

Stage 3 · Code graph Deterministic

In
packages/hoppscotch-common/src + locales/en.json at tag 2026.9.0
Out
code_graph.json: components, render edges, i18n usage, routes, import graph, symbols with line ranges
Fails when
A .vue file fails to compile. That is a hard error listing the file; we don't skip it silently.
  • A small Node helper (extract_vue.mjs) uses the real Vue compiler (@vue/compiler-sfc) and the TypeScript compiler API. Regex or partial grammars can't parse Vue templates reliably.
  • Component names follow the repo's own rule (directoryAsNamespace): components/http/Request.vue → HttpRequest. Template tags then resolve to files, giving RENDERS edges.
  • i18n usage: static t('…') calls in template and script give USES_KEY. Dynamic keys (t(`tab.${x}`)) are recorded as prefix patterns with lower confidence, so they are neither dropped nor overstated.
  • Routes come from pages/ using the Nuxt route style (realtime/websocket.vue → /realtime/websocket).
  • Line ranges for each SFC block (<template>, <script>, <style>) and each exported TS function. These let a PR diff be classified as a visual, structural or behavioural change.

4c · Requirement → UI retrieve judge

  1. A Neo4j full-text index (Lucene BM25) over element labels and screen labels, queried with each requirement's UI cues, returns the top 15 candidates. Deterministic and explainable.
  2. Claude judges the candidates and returns {verdict: COVERED | PARTIAL | NOT_FOUND, element_ids, rationale}. It votes three times independently; the majority wins, and a 2–1 split goes to the human queue.
  3. Code checks that every cited element_id was among the candidates.

4d · Requirement → code retrieve judge

The same method runs over i18n texts and component names. It answers one question for the absence model: is this feature present in the code at all?

Stage 5 · Probe agent LLM agent, bounded

In
Each UI_OBSERVABLE requirement with no UI evidence after Stage 4
Out
New states and transitions (added to the crawl) plus a saved transcript per episode
Fails when
The step budget runs out, or the agent tries a guarded action (the tool returns an error to the agent, and code never executes it)
  • A plain Anthropic SDK tool-use loop with strict tool schemas: observe, click(ref), type(ref, text), press(key), reset(route), then found(ref, why) or give_up(reason).
  • At most 12 actions per requirement. The guardrails are the same code as in the crawl. found is checked: the element must exist in the state just observed, and the Stage 4 judge then re-checks it.
  • The transcript (“searched these screens, tried these actions”) becomes the evidence on the Gap if nothing is found.
Why here and only here: reaching a buried feature (“run a collection with a dataset”) needs judgement about which control leads where. That is where an LLM agent beats breadth-first search. A missing feature is declared only after both the systematic crawl and a targeted search have failed, so the absence claim is stronger.

Stage 6 · Gaps, flows and graph load Deterministic Flow names

  • Gaps: fixed rules applied to each requirement's presence signature (see section 8).
  • Flows: for each covered requirement, the shortest replayable path from a seed route to its evidence element. Each flow is replayed in a fresh browser to prove it works; a flow that doesn't replay is dropped and logged. Claude only names it (“Add a header to a request”).
  • Reverse absence: UI with no requirement (undocumented features) and components never linked to any crawled element (“dark code”). Both are reported as coverage metrics.
  • Load: idempotent MERGE on stable IDs, uniqueness constraints, and three native full-text indexes. Running it twice gives an identical graph.

7Graph schema

Built to answer three queries well: blast radius, absence, and “is the pipeline lying?”. Every node and edge earns its place in at least one of them.

Blue edges cross layers and carry method, confidence and evidence. The two yellow bridge nodes exist natively in both the UI and the code, so edges through them are observations, not guesses. Left out of the drawing for readability: Requirement → Component (IMPLEMENTED_IN, used by the absence check), Gap → CrawlRun (ASSERTED_IN), Section → Document, and PullRequest → I18nKey (CHANGES).

Edges that cross layers carry their evidence

Every cross-layer edge (COVERED_BY, IMPLEMENTED_BY, IMPLEMENTED_IN, DISPLAYS) has method, confidence, evidence and run_id. The report can then show why each link exists, and the eval can score each method separately.

TRANSITION is a relationship

Path-finding (“shortest way to reach this state”) is a native graph traversal on relationships. The clicked element is stored as a property.

Flow is a node

Flows are named, reported, replay-verified and referenced by requirements. Each step is an ordered STEP edge to an element.

Justified against real queries

// Q1 · Blast radius: what does PR #n put at risk, and through which chain?
MATCH (pr:PullRequest {number: $n})-[ch:CHANGES]->(f:File)
MATCH p = (f)<-[:IMPORTS*0..3]-(g:File)<-[:DEFINED_IN]-(c:Component)
MATCH (e:Element)-[impl:IMPLEMENTED_BY]->(c)
WITH e, impl.confidence * ch.weight * (0.7 ^ (length(p) - 1)) AS risk
MATCH (st:State)-[:CONTAINS]->(e)
OPTIONAL MATCH (fl:Flow)-[:STEP]->(e)
OPTIONAL MATCH (r:Requirement)-[:COVERED_BY]->(e)
RETURN e.label, max(risk) AS risk,
       collect(DISTINCT st.label) AS screens,
       collect(DISTINCT fl.name)  AS flows_to_retest,
       collect(DISTINCT r.id)     AS requirements_at_risk
ORDER BY risk DESC
// Q2 · Absence: testable requirements with no UI evidence, and why
MATCH (r:Requirement)-[:HAS_GAP]->(g:Gap)
WHERE g.kind IN ['UNOBSERVED_IN_UI', 'NOT_FOUND_ANYWHERE']
OPTIONAL MATCH (g)-[:EXPECTED_IN]->(c:Component)
MATCH (g)-[:ASSERTED_IN]->(run:CrawlRun)
RETURN r.statement, g.kind, g.probe_summary,
       collect(c.name) AS code_says_it_lives_in, run.id
// Q3 · Pipeline honesty: every requirement is covered XOR has an explained gap.
// Must return zero rows on every run (an automated invariant).
MATCH (r:Requirement)
WITH r, EXISTS { (r)-[:COVERED_BY]->() } AS covered,
        EXISTS { (r)-[:HAS_GAP]->() }   AS gap
WHERE covered = gap
RETURN r.id, covered, gap
Why Q1 shapes the schema: the PR enters the graph through File and leaves through Element. Everything a QA lead cares about (screens, flows, requirements) is one hop from Element. That's why Element is deduplicated across states and why flows point to elements rather than to states.

Why a Gap node, rather than a property or a missing edge

1 · Absence needs provenance

“Not found” is only true relative to a crawl (its budget and boundary) and a search (candidates checked, probe actions tried). A node can hold that evidence and link to the CrawlRun and to the screens searched.

2 · Absence changes over time

A re-crawl can resolve or confirm a gap. first_seen and last_seen give a history, which a boolean property can't.

3 · Open world vs closed world

A missing edge can't be told apart from “we never computed it”. Explicit gaps make closed-world claims only where we did the work, which is what Q3 checks.

4 · Gaps take part in blast radius

EXPECTED_IN → Component means a PR touching a component behind an unverified feature shows up in the report, instead of disappearing.

9Confidence under ambiguity, and when to ask a human

Principle: confidence belongs to the evidence, not to the model's mood. An LLM's self-reported certainty is not calibrated, so we never use it as a number.

Propagation: an item's risk is the strongest single evidence chain: max over chains of (product of edge confidences × change weight × 0.7hops). We use max rather than noisy-OR because chains through the same component are correlated, and the strongest single chain is something we can show a person.

High ≥ 0.75

“Retest this.” Shown first, with steps and a screenshot.

Medium 0.40–0.75

“Worth a check.” Shown with the evidence chain.

Low < 0.40

Appendix only, as weak signals. Not presented as at risk.

The system stops and asks a human when…

#TriggerExample
1The judge's votes split 2–1 on a requirementIs the “Runner” button evidence for “run a collection with a dataset”?
2A PR changes UI-package code that maps to no crawled element and isn't known to be out of scopeA helper only the CLI uses, or a screen the crawl never reached?

How the asking works: each trigger creates a ReviewItem with its evidence attached. triangulate review walks a human through them, and answers are saved to a versioned overrides.yaml that every later run replays. The pipeline still finishes: the report gets a “Needs a human” section, and --strict makes the run exit non-zero so CI can block on open items.

“If we ran it 100 times, which runs were correct?”

Correct means matching the gold sets, not each other

A run is correct if it passes every invariant and meets the G1–G3 thresholds. Agreement between runs measures stability. Accuracy is measured against labels.

Find divergence by stage

Each stage writes hashed artifacts. When run 37 differs, comparing hashes stage by stage shows where it diverged (e.g. Stage 4c voting), not just that it did.

Reproducibility is designed in, not hoped for

Claude Opus 5.5 does not accept a temperature setting, so we can't “set temperature to 0”. Instead every LLM response is cached by a hash of model + prompt, so replaying a run is bit-identical. Variance is measured deliberately, with the cache off.

The live app can drift

The crawl records the app version at the start and end. A run where the version changed is invalid by definition, which separates our variance from the app's.

12“No fallback” rules

What your instruction means in practice for this system.

Fail fast and loud

A stage that can't meet its contract raises with a clear message: unknown version, invalid LLM schema, Neo4j unreachable, a .vue file that won't compile. No quiet “best guess” output.

No hidden alternate paths

No second model, provider or heuristic quietly takes over. A model refusal stops the stage and is surfaced. Server-side model fallback is deliberately left off.

Every inference is labelled

Each link says which method produced it. Inferred is never shown as proven, and the report separates the two.

Uncertainty goes to a person, not to a guess

Where an ordinary system would fall back, ours raises a review item. Network retries with backoff remain: those repeat the same operation and are not fallbacks.

13Scope: what goes deep, what's scoped, what's cut

The brief rewards depth on two layers with an honest cut on the third. The PR enters through code and its consequences show up in the UI, so those two layers and their link go deep. Requirements are the lens we report through.

Deep

  • DOM↔code linking (i18n + route render tree + neighbour tie-break), measured per method
  • PR → blast radius: hunk classification, transitive imports, coverage loss, drift check
  • Absence model with evidenced Gap nodes and the probe agent
  • The non-engineer report, with a validator that enforces it

Scoped down (stated in the doc)

  • Requirements: only the 26 feature pages; one extraction pass; no history of doc versions
  • Crawl: logged-out web UI only; 250 states, depth 6; one viewport; English
  • Code: hoppscotch-common frontend only; dynamic keys and components only partly resolved
  • PR analysis uses the static graph; the PR build itself is not run

Cut

  • Logged-in crawling (teams, workspaces, tokens)
  • Desktop app, CLI, backend (NestJS) code
  • Visual regression and screenshot diffing
  • Test generation
  • A custom graph UI (use Neo4j Browser instead)
  • Generalising to other apps (the method is general; the claims are not)

18With another week: three things, in order

1 · Runtime ground truth for DOM↔code

Build the app from source at the pinned tag with a tiny Vite plugin that stamps every element with data-src="file:line", then crawl that local build. The element → component map becomes exact, which replaces the heuristics as the gold standard and calibrates every confidence number automatically. First, because every downstream answer inherits this layer's accuracy.

2 · Verify predictions by running the PR

Build the PR head locally and re-crawl only the flows in the blast radius, then compare DOM and screenshots before and after. “At risk” becomes “changed” or “broken”, with evidence. As a side effect, every future PR becomes a labelled eval example, so the eval improves itself over time.

3 · Logged-in coverage via self-hosting

Run Hoppscotch self-hosted in Docker with a seeded test account, and crawl workspaces, teams and tokens. This turns the largest gap class (OUTSIDE_CRAWL_BOUNDARY) into evidence, using credentials we create ourselves on our own instance.

Also worth doing, but lower value: a PR-comment bot for CI, incremental crawls keyed to changed routes, and embeddings alongside BM25 retrieval.
