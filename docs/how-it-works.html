Triangulate · plain-language guide

What we built, and how it works

When a developer changes the code, Triangulate tells the QA team which screens, user journeys and documented features to retest, and why. It does this by joining three sources that are normally kept apart: the product docs, the live app, and the source code.

1The problem in one minute

A pull request (PR) changes a few files. But one file can be used by many screens, and a small change can break a feature far away from where the edit was made. A QA lead has to answer: "What should I retest?"

Each source only knows part of the answer:

Docs: what should exist

"You can filter your history with the Filter button." The docs don't know about code.

Live app: what was built

The real screens and buttons a user sees. The app doesn't know which file draws which button.

Code: how it was built

Files, components and imports. The code doesn't know which documented feature it serves.

Triangulate connects all three, so a changed file can be followed to the buttons it draws, the screens those buttons are on, the user journeys that pass through them, and the documented features they deliver.

The target app is Hoppscotch, an open-source API client. Its live app, its code and its docs are all public, and the live version (2026.9.0) is matched to the exact same code release.

There are two separate jobs:

  1. Build the graph (once per app release, about 30 minutes): read the docs, read the code, explore the live app with a browser robot, and link everything together. Command: triangulate run.
  2. Analyse a PR (seconds per PR): take the PR's changed lines, walk the graph outward, and write a plain-English report. Command: triangulate reason 6706.

Here is a shortened version of the report for hoppscotch/hoppscotch#6706 ("support comments in saved response examples"). The full report is in samples/pr-6706/report.html, with screenshots.

The app now accepts JSON with comments in saved response examples; this touches how response bodies are parsed and formatted.

Screens affected (6)

  • REST response view: Filter, More, Wrap lines
  • Response options menu: Clear Response, Filter, Generate Data Schema, More, Wrap lines
  • … and 4 more response views

Product requirements

  • At risk: "You can filter your history by clicking on the Filter button" (with a link to the doc page)

Every line in the report comes from the graph. The AI only writes the sentences, and a checker rejects any text that mentions an id that is not in the computed result, skips a high-risk item, or uses code words such as file names.

5The key trick: connecting a button to its code

The browser shows the button "Wrap lines". How do we know which file draws it? Hoppscotch never writes screen text directly in the code. Every label lives in a translation file, and components ask for it by key. So the visible text is a fact we can look up:

When only one component on the page uses the key, the link is certain. On the hand-checked test set those links were 100% correct. When several could, the one whose other labels best match the neighbouring buttons wins, and its lower confidence is recorded. Controls whose text is not in the translation file (user data, example values) are reported as "not linked" rather than guessed: 70% of controls are linked.

7Handling things that are missing

"We didn't see feature X" can mean very different things. It might be broken, behind a sign-in, or simply not reached. Triangulate never leaves a requirement silently unlinked: each one is either covered, or carries exactly one Gap with a reason.

Risk is arithmetic, not opinion. Each item's risk is its strongest chain: how much the change matters × how sure the button→code link is × how far away it is. High is 0.75 and above, Medium is 0.40 and above, and the rest is Low.

Two lessons from testing on real PRs shaped this:

  • Imports are not behaviour. A PR that only added an import line once flagged 18 controls; now it flags 0.
  • Presence must be confirmed. One PR first listed 24 screens, most of them unrelated editors with their own "Wrap lines" button. With the presence rule it lists 6, all of them response views.

9Confidence, and when a person is asked

Where confidence comes from

Confidence is not guessed. Each linking method's precision is measured on hand-checked examples, and that number becomes the confidence of every link the method makes. With 12 of 12 correct, the confidence becomes 0.93, not 1.0, because a small sample cannot prove perfection.

A person adopts a new measurement on purpose (triangulate eval --update-calibration). It never changes silently between runs.

The system stops and asks when

  • the AI judge cites something it was not shown, or says "covered" without evidence;
  • a PR changes screen code that no seen control maps to;
  • a High-risk item rests on an uncertain link;
  • a feature is not found anywhere.

Answers given in triangulate review are saved and reused on every later run.

10How we know it is right

10 automatic checks on every run

For example: every quote is word-for-word in the docs, every requirement is covered or has exactly one gap, every journey was replayed successfully, every AI citation was a real candidate, and the app version did not change during the crawl.

3 hand-checked answer sets

42 buttons whose code was checked by reading the source; 24 requirements labelled covered or not before looking at the AI's answers; 5 real PRs whose expected impact was written from the diff first.

A pass/fail verdict

A run counts as correct when all checks pass and its scores meet eval/thresholds.yaml. triangulate eval prints the verdict and fails loudly otherwise.

Exact repeat

Every AI answer is saved by a fingerprint of the question, and every stage's output is fingerprinted. Re-running offline reproduced the real run exactly, with zero AI calls.

"If we ran it 100 times, which runs were correct?" Correctness is judged against the hand-checked answers, not against other runs. Agreement between runs measures stability, and the stage fingerprints show where two runs differed. Getting the crawler to repeat exactly needed several real fixes. For example, it now waits until "Connecting…" labels, page reloads and on-demand code downloads have finished before it records a screen.

12Run it yourself

# 1. install (Python 3.12 via uv, Node 20+, a local Neo4j)
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -e ".[dev]"
.venv/bin/python -m playwright install chromium
npm install --prefix src/triangulate/code/node
cp .env.example .env            # add the Gemini key and Neo4j login

# 2. build the graph (offline = use only saved AI answers, no API calls)
.venv/bin/triangulate run --offline

# 3. analyse a pull request
.venv/bin/triangulate reason 6706 --offline   # -> runs/latest/reason/pr-6706/report.html

# 4. check it: 10 checks + scores -> "run is correct" or what failed
.venv/bin/triangulate eval

# 5. answer the open questions (saved for every later run)
.venv/bin/triangulate review

Each run writes everything to runs/<run id>/. Sample reports for five real PRs are in samples/, and the full design reasoning is in docs/DESIGN.md.

13Words used here

Requirement
One short, testable statement from the docs, with its exact quote and a link to the page.
Screen (state)
One distinct view of the app, for example the REST page with a menu open.
Control (element)
A button, field, tab or link on a screen. The same "Send" button on many screens is one control.
Component
A reusable building block in the code (a .vue file) that draws part of a screen.
Text key
The id of a label in the translation file, for example state.linewrap = "Wrap lines". It is the bridge between screen and code.
User journey (flow)
A recorded click path from a starting page to a feature, replayed to prove it still works.
Gap
The recorded reason a requirement is not covered: needs sign-in, not reached, not web UI, or not found.
Blast radius
Everything a code change can affect: controls, screens, journeys and requirements.
Offline run
A run that reuses saved AI answers and makes no API calls; it reproduces a run exactly.
Knowledge graph
A database of things and the links between them (here: Neo4j), which can be walked from any starting point.
